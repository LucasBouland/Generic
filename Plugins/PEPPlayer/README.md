# PEPPlayer

`PEPPlayer` owns player-level behavior independent of the controlled Pawn: its controller, local input state and player lifecycle coordination. `PEPPlayerUI` owns the player's presentation and depends on `PEPCoreUI`. The player module only knows the `IPEPPlayerHUDContract`; it does not depend on the concrete HUD implementation.

The controller currently derives from GMC's player controller and uses Enhanced Input. These are direct dependencies of `PEPPlayer`, not of `PEPCore`. The plugin declares CommonUI because `PEPPlayerUI` builds on `UCommonUserWidget`.

Domain UI modules that need to react to the player menu state depend on the `PEPPlayer` module but should use `IPEPPlayerMenuHost` (`Player/PEPPlayerMenuHost.h`) instead of including `APEPPlayerController`: `Cast<IPEPPlayerMenuHost>(PlayerController)` exposes `OpenMenu`, `CloseMenu`, `IsMenuOpen`, `GetPlayerInputState` and `GetOnPlayerInputStateChanged()`. `EPEPPlayerInputState`, `EPEPGameplayInputMode` and `FOnPEPPlayerInputStateChanged` live in the lightweight `Player/PEPPlayerInputTypes.h`.

## Configuring the current player menu

1. Set the GameMode's Player Controller class to a Blueprint derived from `APEPPlayerController`. Use `EnhancedInputComponent` as the project's default Input Component Class. Use `EnhancedPlayerInput` as the controller's input class.
2. Reparent `WBP_PEP_HUD` to `UPEPPlayerHUD` from `PEPPlayerUI`. It uses a `WidgetSwitcher` named `HUDSwitcher` with direct child UserWidgets named `GameplayScreen` and `PlayerMenuScreen`. Those three names are required by `BindWidget`; incompatible or missing widgets fail Blueprint compilation. Screen selection uses widget references, so designers may reorder the children. Assign the class to `PlayerHUDClass` on the controller. Do not create a duplicate HUD in Blueprint.
3. Create Boolean press actions `IA_TogglePlayerMenu` (mapped in gameplay and menu IMCs), `IA_OpenPlayerMenu` (optional opening key in the gameplay IMC), and `IA_ClosePlayerMenu` (Escape in the menu IMC). Assign `ToggleMenuAction`, `OpenMenuAction`, `CloseMenuAction` and `MenuMappingContext`. Each action binds once on `Started`; remove duplicate Pawn bindings. The fields are optional, so Toggle alone or Open/Close alone also works. Avoid mapping multiple state actions to the same key in one active context. If the same asset is assigned to multiple fields, only one binding is made and dispatch precedence is Toggle, Close, Open; use distinct assets for distinct semantics.
4. Populate `GameplayMappingContexts` with every context that provides Pawn gameplay input. The Pawn installs/removes those contexts normally; the controller suspends only currently active contexts and remembers their priorities. The controller owns installation/removal of the menu context. Independent contexts that remain active should contain only commands allowed during the menu.
5. Optionally assign Boolean press actions in `MenuCommandActions`, map them in `IMC_PlayerMenu`, and handle `OnMenuCommand` to switch tabs or issue UI commands. Buttons may call `CloseMenu` directly. `ToggleMenu`, `OpenMenu` and `CloseMenu` are also callable from Blueprint.
6. In `UPEPPlayerHUD::OnControlledPawnChanged`, detach the previous Pawn's delegates and attach the new Pawn's data. The new Pawn may be null. Use the owning controller; do not use `GetPlayerController(0)`.
7. Choose the gameplay cursor policy on the controller. Defaults (`GameplayInputMode = GameOnly`, `bShowMouseCursorInGameplay = false`) suit action games: hidden cursor, viewport-only input. Strategy/RTS games set `GameplayInputMode = GameAndUI` and `bShowMouseCursorInGameplay = true`: the cursor stays visible during capture and Slate gets first access to input, with focus on the game viewport. `GameOnly` with a visible cursor is possible but the viewport hides the cursor while it captures the mouse. For mouse locking (edge scrolling) or another focus target, override the protected virtual `ApplyGameplayInput`, which runs at BeginPlay and after every menu close.

Opening the menu removes the registered gameplay contexts and adds the menu context, displays the menu, shows the cursor and applies Game And UI with menu focus. Closing reverses those changes, cancels this player's drag-and-drop and reapplies the gameplay input policy, which returns this player's focus to the game viewport. Movement/look ignore calls are balanced without resetting another system's locks. A valid possessed Pawn is required; possession changes close the menu. Context rebuilds are deferred to the engine's normal rebuild point, outside input delegate execution.

Game And UI gives Slate first access to input. The HUD's preview handler forwards key presses to `APEPPlayerController::RouteMenuShortcut`, which scans the live Enhanced Input mappings once per press (active contexts and player remaps, no allocation, no cached table to invalidate). It consumes handled keys and repeats to prevent focused children from swallowing close actions or causing duplicate dispatch. The bridge only sees keys while this player's focus is inside the HUD; with focus on the game viewport, keys follow the plain Enhanced Input path. Rules:

- Only Boolean press mappings are bridged: no trigger, `Down` or `Pressed`. Mappings using Hold, Tap, Released, Pulse, combo or custom triggers (on the mapping or the action) are left to the normal Enhanced Input path.
- Chords are bridged when the chord action is mapped to modifier keys (Shift, Ctrl, Alt, Cmd): the chord must be held, the most specific chord wins (Shift+Tab over Tab) and the blockers Enhanced Input injects on the unchorded mapping are honored. Chords on other keys are not evaluated; those mappings stay on the Enhanced Input path.
- Ctrl, Alt or Cmd held without a chord requiring them suppresses the mapping (Ctrl+Tab does not trigger a plain Tab shortcut). Focused children may still handle the key; if they decline it, the HUD consumes it so Enhanced Input cannot fire the plain mapping through the viewport. Shift alone is tolerated.
- When the event's Slate user focuses an editable text (`SEditableText`, `SMultiLineEditableText`, so text, search and spin boxes), the text field sees the key first. Keys it leaves unhandled bubble back to the HUD: non-typing keys (Escape, Tab, gamepad buttons) route normally; typing keys mapped to a menu shortcut are swallowed without dispatch so they cannot reach Enhanced Input through the viewport while the player types. Custom Slate text widgets need `IsTextEntryFocused` overridden.

Mouse events, analog axes and gamepad input consumed by CommonUI before Slate key routing follow the normal CommonUI / Enhanced Input path and need project-specific navigation validation. Modal policies remain the project's responsibility.

Split screen: focus changes go through `SetInputMode`, which targets only this player's Slate user, and drag cancellation uses this player's Slate user. Mouse lock, capture mode and cursor hiding during capture are settings of the shared game viewport client, so the last player applying an input mode decides them for every player; the hardware cursor is shared as well.

Held Boolean keys are suppressed until release during context restoration. This does not provide custom axis/gamepad-neutral tracking. Axis handlers should clear stored intentions on termination, and analog controls may resume while still held. Removing a mapping context does not stop independent timers, abilities or latched gameplay states that ignore input termination. Do not use `DisableInput`, `EnableInput` or `ClearAllMappings` in menu callbacks.

The retained widget avoids recreating the screen, but does not guarantee prebuilt list entries, loaded assets or a precomputed Slate layout.

## Validation

Build the editor target, then validate in standalone and as an owning multiplayer client: remapped open/close keys; closing while a child button has focus; typing shortcut letters and pressing Escape in a menu text box; Ctrl/Alt combinations and Shift chords; holding the shortcut; both gameplay input modes with and without a visible cursor; split screen focus and drag-and-drop; input cleanup when opening during an active action; held Boolean keys and movement axes on return; drag-and-drop; unpossess/destroy/switch Pawn while the menu is open; rejected opening without a Pawn; camera capture on return; alt-tab. Compilation does not verify Blueprint input cleanup, mappings or real Slate mouse capture.
